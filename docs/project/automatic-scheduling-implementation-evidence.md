# Automatic Scheduling Implementation Evidence

This document records the static implementation handoff for the frozen requirement delta introduced by `US-6.1` and the related revisions to `US-1.2`, `US-2.2`, `US-3.1`, `US-3.3`, `US-4.1`, and `US-5.1`.

No automated validation was executed in the sandbox. Every command below is for local execution.

> **Requirement supersession notice — 2026-08-03:** US-6.3 introduces Task
> Capacity Allocation Percentage and concurrent same-assignee planned allocation,
> and US-6.2 now uses Actual-Date-only, Actual-versus-Actual balanced/rebalanced Actual Allocation instead of the Execution-baseline/capacity-debt algorithm.
> The tables below remain the historical US-6.1 baseline and must be interpreted
> through US-6.3 supersession. Current US-6.3 and revised US-6.2 evidence is
> recorded in
> [`task-capacity-allocation-implementation-evidence.md`](task-capacity-allocation-implementation-evidence.md);
> obsolete serial/non-preemptive test names in this file are not current evidence.

> **Capacity rounding clarification — 2026-07-30:** the current explicit user instruction supersedes the earlier wording in the frozen RD-01 snapshot. Execution Capacity is rounded once after Member Buffer. Commitment Capacity is calculated independently from Resolved Daily Capacity after Member Buffer and Project Buffer, then rounded once. Both final capacities use the nearest `0.5` hour.
>
> **WBS create-trigger clarification — 2026-07-31:** a Name-only root or child create is not a scheduling-relevant mutation. It persists an empty Task without invoking portfolio recalculation. Create remains a trigger only when it also performs executable-to-group structural conversion and moves executable state or dependency endpoints.

## Frozen Delta Coverage

| Delta | Cross-story consequence |
|---|---|
| RD-01 | Base Execution Capacity replaces the old member-level Commitment label while preserving deterministic `0.5`-hour rounding after Member Buffer. |
| RD-02 | `automaticScheduling` is the only activation toggle; `autoDependencyByAssignee` is removed. |
| RD-03 | Executable Task owns persisted integer `lag`. |
| RD-04 | Capacity precedence is weekend/holiday, override, member capacity, Member Buffer, then Project Buffer. |
| RD-05 | Concrete independent Execution and Commitment daily allocation is persisted. |
| RD-06 | Dependency ownership is manual, automatic, or both, projected once. |
| RD-07 | Fit-based automatic blocker reconciliation preserves manual ownership. |
| RD-08 | Covered mutations and scheduling share one transaction. |
| RD-09 | Completed and Locked work is fixed; Closed Projects are excluded. |
| RD-10 | Scheduling is serialized, versioned, rollback-safe, and stale projections are rejected. |
| RD-11 | Generated dates are read-only in automatic mode; reasons and ownership are accessible. |
| RD-12 | Changed stories and project documentation are reconciled to the concrete implementation. |
| RD-13 | Name-only WBS create skips scheduler; scheduling-relevant structural conversion create remains atomic and scheduled. |

## Cross-Story Evidence Notes

- `US-1.2`: Base Execution Capacity preview rounds to `0.5` hours; Commitment Capacity is not a member-level preview.
- `US-2.2`: Public Holiday forces zero capacity and mutations are consumed on the next scheduling trigger.
- `US-3.1`: active Priority is unique; duplicate Priority is a data-integrity conflict, not a tie-breaker case. Lock/Close/Reopen lifecycle changes coordinate the active portfolio in one transaction.
- `US-3.3`: `automaticScheduling` is the only activation flag. OFF preserves dates as manual/fixed values; ON without an anchor persists an explicit unscheduled state.
- `US-4.1`: Lag is Task-owned; generated Execution/Commitment dates are scheduler-owned in automatic mode. Name-only create leaves those dates empty without invoking scheduling; structural-conversion create remains atomic with scheduling.
- `US-5.1`: one endpoint can be manual, automatic, or both; manual unlink never destroys valid automatic ownership.
- `US-6.1`: concrete scheduler, allocation projection, reconciliation, transaction, concurrency, versioning, and stale-response protection are implemented.
