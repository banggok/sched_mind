## Execution Configuration

Use the following configuration as authoritative:

EXECUTION_MODE:
[LOCAL_WORKTREE | UPLOADED_ARCHIVE]
UPLOADED_ARCHIVE

REQUIREMENT_ROOTS:
[user_story/]

VALIDATION_MODE:
[USER_LOCAL_VALIDATION | AGENT_VALIDATION]
USER_LOCAL_VALIDATION

DELIVERY_MODE:
[DIRECT_WORKTREE | CHANGES_ONLY_ZIP]
CHANGES_ONLY_ZIP

Additional task instruction:

[OPTIONAL — INSERT EXPLICIT USER INSTRUCTION HERE]

Interpretation:

- `LOCAL_WORKTREE`
  means work directly in the current local Git repository.

- `UPLOADED_ARCHIVE`
  means locate the latest uploaded repository archive, extract it once, and
  work on that extracted repository.

- `USER_LOCAL_VALIDATION`
  means author all required tests but do not execute automated validation.
  The user will run validation locally, but you still have to do static review to minimize issue in local validation

- `AGENT_VALIDATION`
  means execute repository-supported targeted and full validation according
  to AGENTS.md and project documentation.

- `DIRECT_WORKTREE`
  means changes remain directly in the current working tree and no ZIP is
  required.

- `CHANGES_ONLY_ZIP`
  means create a ZIP containing only the files required to apply the
  implementation, preserving repository-relative paths.

Do not silently change these configuration values.

If any configuration value is missing or invalid, stop before editing and ask
for the missing value.

## Mandatory Initial Git Snapshot

Before modifying any repository file, capture and freeze:

1. Initial Working Tree Snapshot.
2. Initial Requirement Delta Snapshot.
3. Requirement Delta Matrix.

These three artifacts define the implementation boundary for the entire task
and all continuation turns.

### A. Initial Working Tree Snapshot

Run:

git status --short
git diff --name-status --find-renames
git diff --cached --name-status --find-renames
git ls-files --others --exclude-standard
git diff --stat
git diff --check

Record:

- every modified tracked file;
- every staged file;
- every untracked file;
- every renamed file;
- every deleted file;
- which changes are inside the configured REQUIREMENT_ROOTS;
- which changes are outside the configured REQUIREMENT_ROOTS.

Initial changes outside REQUIREMENT_ROOTS are pre-existing user changes.

Preserve them.

Do not automatically interpret them as requirement input.

They become implementation scope only when the frozen requirement delta
demonstrates that they are affected.

### B. Initial Requirement Delta Snapshot

For every configured REQUIREMENT_ROOT, capture:

git diff --name-status --find-renames -- <REQUIREMENT_ROOT>
git diff --find-renames -- <REQUIREMENT_ROOT>
git diff --cached --name-status --find-renames -- <REQUIREMENT_ROOT>
git diff --cached --find-renames -- <REQUIREMENT_ROOT>
git ls-files --others --exclude-standard -- <REQUIREMENT_ROOT>

The complete initial Git delta under REQUIREMENT_ROOTS represents every
requirement change since the last implemented baseline.

It may include:

- unstaged modifications;
- staged modifications;
- untracked files;
- renamed files;
- deleted files.

Do not rely only on `git diff`.

For untracked requirement files, read the complete file because no historical
diff is available.

For deleted requirement files, inspect the baseline version through Git when
available.

### Frozen Scope Rule

Freeze the Initial Working Tree Snapshot and Initial Requirement Delta Snapshot
before editing.

After implementation begins:

- never recalculate requirement scope from the current Git diff;
- never treat agent-created code, test, documentation, or evidence changes as
  new requirement input;
- never lose staged, unstaged, untracked, renamed, or deleted requirement
  entries from the initial snapshot.

The working-tree diff will become mixed with implementation output.

The frozen Initial Requirement Delta Snapshot remains authoritative throughout
the task and every continuation turn.

If no requirement delta exists under REQUIREMENT_ROOTS:

1. Do not invent implementation scope.
2. Do not edit production code.
3. Return a checkpoint stating that no requirement change was detected.
4. Identify any explicit task instruction that might intentionally override
   the absence of a Git requirement delta.

## Requirement Authority

Use this precedence:

1. Explicit instruction in the current user prompt.
2. Frozen Initial Requirement Delta Snapshot.
3. Complete current content of changed requirement files.
4. Current unchanged authoritative project requirement documentation.
5. Architecture documentation.
6. Existing production code.
7. Existing tests.

Existing code and tests represent previous behaviour.

When a newer requirement introduces an exception to an older rule:

- implement the exception;
- preserve the old rule outside the exception boundary;
- revise tests that incorrectly enforce the old rule as absolute;
- reconcile older documentation where required.

When authoritative requirement sources still contradict each other:

1. Identify the exact files, sections, and statements.
2. Apply the authority order.
3. Continue implementing unaffected deltas.
4. Do not invent a missing business rule.
5. Return a checkpoint if the contradiction cannot be resolved.

## Test Authoring Standard

Every authored or revised test must:

- have a clear scenario-based name;
- identify the relevant AC or Delta ID where practical;
- assert observable behaviour;
- distinguish before and after state;
- avoid snapshot-only evidence;
- avoid mock-call-only evidence;
- verify persistence where applicable;
- verify rollback by reading state again;
- use genuine concurrent execution for concurrency cases;
- control response ordering for stale-response cases;
- explicitly verify identity preservation;
- explicitly verify fields that must remain unchanged;
- verify dependency endpoints, not only relation count;
- verify focus and keyboard behaviour for accessibility scenarios;
- avoid unsafe type assertions;
- avoid ambiguous fixtures.
